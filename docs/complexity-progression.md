# Complexity progression

Rebuild Labs should gain structure only when real cases expose a recurring
need. A comprehensive domain guide does not require a general migration
platform on day one.

## Current position

The bootstrap is a **domain module with an experimental capability bundle**:

- shared direction, baseline, asset, evidence, and decision vocabulary;
- complete and incremental human playbooks;
- an initial primary-source research synthesis;
- narrow evaluation cases designed to challenge both mode-selection errors;
  and
- canonical planning and implementation skills with a generated experimental
  Codex adapter.

Repository checks establish structural consistency, not that these protocols
improve real rebuild outcomes.

## Domain maturity

| Stage | Evidence |
| --- | --- |
| Exploratory | Proposed model is grounded in sources and motivating examples. |
| Described | Terms, records, and user jobs have explicit boundaries. |
| Evaluated | Held-out scenarios and real replays expose success and failure modes. |
| Measured | Multiple materially different rebuilds support comparative claims. |
| Stable | Versioned contracts and capabilities demonstrate compatible use and revision. |

## Product maturity

| Stage | Meaning |
| --- | --- |
| Internal | Canonical capability can be exercised from source. |
| Experimental | Installable adapter exists with visible limits and provenance. |
| Preview | Interface is deliberately offered to external consumers with evidence. |
| Stable | Compatibility, release, support, update, and rollback are explicit. |

Product maturity never proves domain maturity. An installable skill remains an
experimental projection until behavior is evaluated.

## Growth sequence

```text
sources and motivating cases
            |
            v
semantic domain model and guides
            |
            v
controlled cases and one executable replay
            |
            v
canonical capabilities
            |
            v
generated product adapter
            |
            v
multi-project measurements and stable contracts
```

Add a versioned JSON schema only when at least two records or consumers need a
stable interchange shape. Add a corpus only when a sampling question exists.
Add candidate intake only when outside methods need reproducible comparison.
Add a general runner or separate repository only after an independent domain
demonstrates reuse.

## Revisit triggers

- Repeated rebuild records diverge because shared fields are underspecified.
- A skill decision cannot be tested without a realistic isolated repository.
- Several real rebuilds need the same deterministic architecture or data
  checks.
- External methods or skills must be compared without making them canonical.
- Product adapters require different release or compatibility lifecycles.
- Data size, licensing, privacy, or security conflicts with this repository.

When a trigger appears, record the pressure, smallest new boundary, evidence,
owner, migration, validation, and rollback. Do not add every mature README Labs
subsystem merely because its directory name is familiar.
